# Testing & Quality

统一承接以下能力：
- 测试策略（Vitest / Playwright）
- 系统化调试（先定位根因，再修复）
- 提交前质量门禁（Biome / TypeCheck / Test / Build）

## 何时使用

- 新功能开发完成后，需要补测试或做回归验证
- 遇到 bug、测试失败、构建异常、线上异常行为
- 准备提交代码，需要执行质量检查

---

## 一、根因优先的调试流程（必须先做）

> 原则：**不做根因定位，不给修复方案。**

### Phase 1：根因定位
1. 读完整报错与堆栈，不跳过 warning
2. 稳定复现（明确输入、步骤、环境）
3. 对照近期变更（代码、依赖、配置）
4. 跨层系统逐层加证据日志（入口、边界、输出）
5. 逆向追踪数据流，找到错误值源头

### Phase 2：模式对照
1. 找项目内可工作的相似实现
2. 与当前实现逐项比对差异
3. 确认依赖前置条件（配置/环境/顺序）

### Phase 3：假设验证
1. 一次只提出一个可验证假设
2. 做最小改动验证
3. 失败则回到 Phase 1，禁止叠加“碰碰运气修复”

### Phase 4：修复与回归
1. 先写失败用例（单测或最小复现脚本）
2. 只改根因点，不顺手大重构
3. 验证目标问题 + 相关回归全部通过

## 二、测试策略

### Vitest（单测）
- 覆盖重点：actions、services、关键纯函数
- 推荐位置：就近 `__tests__/` 目录，命名 `*.test.ts`
- Mock 原则：边界处 mock；优先 `vi.spyOn`；每例后 `vi.clearAllMocks()`
- 断言原则：优先精确断言（`toEqual`、`toHaveBeenCalledWith`），避免模糊断言
- 目标：关键业务逻辑覆盖率 >= 80%

### Playwright（E2E）
- 位置：`apps/web/e2e/`
- 优先覆盖关键路径（登录、核心业务流）
- 等待策略：条件等待（`expect(...).toBeVisible()` / `waitForLoadState`），禁止固定超时等待
- 选择器优先级：`data-testid` > `getByRole` > CSS

---

## 三、提交前质量门禁（顺序执行）

1. `pnpm biome check .`
2. `pnpm type-check`
3. `pnpm test`
4. `pnpm build`（可选但推荐）

任一步失败，先修复再继续，不跳步。

---

## 四、常见反模式

- 未定位根因就直接“尝试修复”
- 多个修复混在一次提交，无法确认有效改动
- 只改现象层，不写回归测试
- 只测边缘路径，不测主流程
- 提交前跳过类型和测试

---

## 五、输出要求

处理测试/调试任务时，输出应包含：
1. 根因结论（证据）
2. 修复点（最小改动）
3. 新增/更新测试点
4. 质量门禁执行结果

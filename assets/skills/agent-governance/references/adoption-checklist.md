# Capability Adoption Checklist

Use for third-party review, cross-project activation, or retirement.

## Inspect

- Pin canonical source, revision, license, and local asset.
- Inspect scripts, hooks, network, credentials, writes, auto-update, and external tools.
- Define the activating intent and adjacent anti-triggers.
- Identify the maintained capability or project rule it overlaps.

Marketplace presence is not proof of project fit. Reject opaque execution, probability-based mandatory invocation, and workflows that chain unrelated skills.

## Place

- Global: narrow, reusable, no project facts.
- Project-scoped: depends on local code, commands, credentials, products, or gates.
- Reference-only: useful knowledge without justified activation.
- Explicit mode: a heavier methodology deliberately selected for suitable work.
- Deprecated/blocked/rejected: superseded, redundant, unsafe, or over-broad.

## Prove

- Run schema and focused regression tests.
- Inspect global and every affected project render.
- Sync and prove both addition and cleanup.
- Audit actual runtime state.
- Run trigger and anti-trigger scenarios.
- For behavior claims, compare native and candidate live runs using outcome, Skill reads, tool calls, retries, and elapsed time.

Do not adopt a capability that cannot be pinned, inspected, scoped, removed cleanly, or shown to improve representative outcomes.
